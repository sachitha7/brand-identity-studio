# Content architecture

What a brand book must say, and in what order. This is the strategy layer —
pair with `page-system.md` for how it's laid out and `mockups.md` for how the
applications get photographed.

## Order of work

Brand work starts from evidence, not taste. Before writing a positioning
line, find out what the business actually sells, to whom, at what price,
through which channel. A brand book written ahead of that is decoration.

1. **Harvest what exists.** Client catalogues, packaging, ad creative, the
   website. Extract the real logo files and sample the real hex values from
   them — never invent a palette when the brand already ships one.
2. **Read the commercial position.** Price point, channel, competitor set.
   A brand book that contradicts the go-to-market plan is worse than none.
3. **Write the strategy pages first** — brand idea, pillars, tone of voice.
   The visual system is downstream of them.
4. **Then document the system** — logo, colour, type, graphic elements.
5. **Then show it applied** — the application pages are what the client
   actually flips to first.

## Two kinds of engagement — know which one you're in

**Documenting an existing brand** (a brand book *of* the current identity)
and **proposing a new one** (a rebrand) are different deliverables that read
almost identically if done carelessly. Before writing anything, confirm
which the client is asking for:

- If they say the current brand, product, or website has *failed
  commercially*, they are not asking for a careful record of it — they are
  asking for what replaces it. Sampling the existing palette and
  photographing the existing product in that case produces the wrong
  document, however accurate it is.
- If they want the current identity written up for internal use, handoff,
  or a printer, faithful documentation is correct and a rebrand would be
  presumptuous.

When in doubt, ask. Getting this wrong wastes an entire build.

## Content architecture of a brand book

Include these, in this order. Drop a section only when the brand genuinely
has no such asset; never pad with a section you have nothing to say about.

| Section | What it must contain |
|---|---|
| Cover | Logo on the brand's hero treatment. Nothing else. |
| Contents | Numbered, grouped into movements (the case / the mark / the system / the range / expression / applications / delivery). |
| The case (rebrand only) | Why this exists: evidence the old approach failed, what changes vs. what stays, the competitive frame, one line the whole brand is tested against, 3-4 pillars. |
| The brand (documentation only) | Who makes it, where, what it sells, at what position. Facts. |
| Logo anatomy / why it stays | Deconstruct the mark, or state explicitly why it survives a rebrand intact. |
| Clear-space | Define an `X` unit derived from the mark itself, not an arbitrary mm. |
| Variations | Primary lockup, secondary/stacked, mark alone, wordmark alone, reversed. State where each is used. |
| Misuse | 8-10 specific don'ts, each drawn as the wrong thing, not described. The two that matter most are usually brand-specific — name them. |
| Colour | Every shade with HEX, RGB and CMYK (and Pantone for any foil/spot colour). Name each one. If a colour is "retired" from general use (e.g. an old brand colour kept only inside the logo), say so explicitly. |
| Colour proportion | The ratio the palette is used in. Prevents accent inflation. State the actual contrast ratios checked, and flag any pairing that fails WCAG AA rather than omitting it. |
| Primary / secondary type | The display and text faces, their character sets, and what each is *for*. |
| Type hierarchy | A real scale with sizes, weights and tracking, at a stated reference size (e.g. carton scale), with a rule for scaling it up/down. |
| Gradient / graphic device | Only if the brand has one. Label the exact stops. |
| Patterns | Derived from the mark. Show density variants. |
| The range / naming architecture | Every product with its hero actives/character, size and price. A naming formula the reader could extend to a tenth product. |
| Packaging / provenance | What's on the front (minimal, mandatory fields only) vs. the back (proof, ingredients, origin). |
| Art direction | Photography rules: light, surface, crop, what not to shoot, explicit prohibitions. |
| Tone of voice | Three do/don't pairs written in the brand's actual words, plus the habits that generalize past those three examples. |
| Placements | Where the logo sits on a layout, against a grid. |
| Applications | See `mockups.md` for the full expected set — this is usually thinner than it should be. One page each. |
| Migration plan (rebrand only) | Phased: what happens to existing stock, when old assets retire, the one dependency that could stop the whole plan. |
| Back cover | Copyright line. |

## Writing rules

- **Name every colour and every asset.** "Champagne Leaf" is usable in a
  studio conversation; "the gold one" is not.
- **Every page carries a body paragraph** explaining *why* the rule exists,
  in 60-110 words. This is what makes a brand book usable by a printer who
  has never met the client.
- **Specify, don't suggest.** "Use at least X clear-space on all sides" not
  "try to leave some room".
- **Tone of voice must be written in the brand's tone**, or the page
  disproves itself.
- Use the client's own vocabulary — their SKU names, their fragrance notes,
  their ingredient claims. Generic copy signals the book was not written for
  them.
- **State real limitations, don't hide them.** A colour that fails contrast,
  an active ingredient percentage still awaiting formulator confirmation, an
  inconsistency in the existing range — these belong on the page, framed as
  what to resolve, not edited out. A brand book that only shows the client
  what already works is worth less than one that also tells them what to fix.

## Things that get a brand book rejected

- A palette that does not match the product already on shelf (unless this
  is deliberately a rebrand, in which case say so on page one).
- Forecast-style claims ("will increase recall by 30%"). Brand books state
  rules, not outcomes.
- Typefaces the client cannot license or install. Prefer open families
  (Google Fonts) unless the client already owns a licence.
- Application mockups for channels the client does not use, or — the
  opposite failure — missing the channels they clearly do use. See
  `mockups.md` for the checklist.
